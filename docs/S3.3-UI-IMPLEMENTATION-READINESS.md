## 1) Minimal scope for first UI patch

### In scope (strict minimum)
1. Show top-priority diagnostics in `Pilotage` run cards.
2. Show one compact diagnostic summary in `Historique`.
3. Enforce visual levels:
   - `blocking`
   - `warning`
   - `info`
4. Show operator CTA from matrix where applicable.
5. Explicitly block/hide Apply CTA when a blocking diagnostic exists.

### Diagnostics included in first patch
- `RN_PLAN_DIGEST_MISMATCH`
- `RN_COLLISION_BLOCKING`
- `RG_REQUIRED_METADATA_FIELDS_MISSING`
- `RG_BUNDLE_UNREADABLE_OR_INVALID`
- `RG_RULE_NOT_FOUND_OR_NOT_APPLICABLE`
- `RN_DESTRUCTIVE_GUARD_MISSING`
- `RG_FALLBACK_REASON_PRESENT`
- `AN_EXTRACTION_WARNING_STRUCTURED`
- `RN_IDEMPOTENT_NOOP`

### Minimal rendering shape
- Run Card:
  - short label
  - severity badge
  - primary CTA (if any)
- Historique:
  - highest-priority diagnostic only
  - severity badge + short label
- Run Detail:
  - keep full details (already existing behavior; no heavy redesign)

### Explicitly out of scope
- Full UI redesign/theme work
- New routes or page restructuring
- New backend diagnostic generation logic
- Multi-CTA orchestration per single card
- Bulk remediation actions

## 2) Measurable acceptance criteria
Patch is acceptable only if all points pass:
1. Blocking diagnostics render with blocking visual level in Pilotage and Historique.
2. Warning and info levels are visually distinct and consistent with matrix.
3. CTA matches documented recommendation for each rendered diagnostic.
4. Apply CTA is blocked whenever at least one blocking diagnostic is present.
5. No regression of existing non-diagnostic UI sections in Pilotage/Historique.
6. For runs without diagnostics, existing display remains readable and stable.

## 4) Rollback strategy (documentary)

### When to rollback
- Blocking diagnostics do not block Apply in UI.
- CTA mapping is incorrect or misleading.
- Significant readability regression in Pilotage/Historique.
- Smoke or test regression tied to UI patch.

### What to rollback first
1. Revert new diagnostic rendering in run cards and history summary.
2. Keep pre-existing detail views unchanged.
3. Keep diagnostic data generation untouched (no backend rollback in this scope).

### What must remain stable even after rollback
- S3.2 diagnostic IDs and severity semantics.
- S3.2 UI matrix decisions.
- S3.1 operator decision model (`Go`, `Review required`, `No-Go`).

## 5) Readiness decision
S3.3 is ready to open a first minimal UI patch if:
- this checklist is accepted as implementation gate,
- S3.2 reference/matrix/contract stay the source of truth.

If accepted, implementation should start with a single small UI patch focused only on run card + history diagnostic rendering and Apply blocking behavior.
