# S3.2 Diagnostics UI Contract (minimal)

Date: 2026-04-16  
Scope: contrat documentaire de rendu UI (Pilotage/Historique), sans changement de code

## Purpose
Freeze a minimal, implementation-ready contract for diagnostics rendering, so UI work can start without reinterpreting S2/S3.1 decisions.

## 1) Minimal UI diagnostic shape

Each diagnostic exposed to UI should follow this structure:

```json
{
  "id": "RN_PLAN_DIGEST_MISMATCH",
  "severity": "blocking",
  "summary": "Digest preview/apply incoherent",
  "details": "expected_plan_digest does not match preview plan_digest",
  "cta": "Re-preview",
  "scope": "run",
  "source": "MuniRenommage",
  "display_location": ["run_card", "run_detail", "history"]
}
```

### Field constraints (documentary)
- `id`:
  - required, stable string identifier
  - must map to diagnostics reference IDs
- `severity`:
  - required enum: `info | warning | blocking`
- `summary`:
  - required short operator label (single-line target)
- `details`:
  - optional extended text (for detail view)
- `cta`:
  - optional enum: `Re-run Analyse | Rebuild Bundle | Re-preview | Stop Apply | Aucune`
- `scope`:
  - required enum: `run | chain`
- `source`:
  - required enum-like string: `MuniAnalyse | MuniRegles | MuniRenommage | Orchiviste`
- `display_location`:
  - required array subset of: `run_card | run_detail | history`

## 2) Prioritization and aggregation rules

### Sorting priority
Always sort diagnostics by severity:
1. `blocking`
2. `warning`
3. `info`

Within same severity:
1. stable `id` ordering (lexicographic)
2. then source ordering: `Orchiviste`, `MuniRenommage`, `MuniRegles`, `MuniAnalyse`

### Aggregation when multiple diagnostics coexist
- Run Card:
  - show compact top priority set (max 3 summaries)
  - always include at least one `blocking` if present
- Run Detail:
  - show full list with full `details`
- History:
  - show compact status + key summary (highest-priority diagnostic)

### Deduplication rules
- Same `id` + same `scope` + same `source` -> keep one entry.
- Keep highest severity instance if duplicates differ.
- Merge textual details only in `run_detail` display.

### Compact summary vs full detail
- Compact summary:
  - `id`, `severity`, `summary`, `cta`
- Full detail:
  - all fields, including verbose `details`

---

## 3) CTA rules

### When CTA is allowed
- CTA can be shown when it maps to a valid corrective action for current diagnostic.
- One primary CTA per diagnostic in compact views.

### When CTA must be removed
- Remove CTA when no meaningful action exists (`info` no-op cases).
- Remove CTA if diagnostic is purely informational and non-actionable.

### When Apply must be explicitly blocked
`Apply` must be disabled/hidden if at least one `blocking` diagnostic is present, including:
- `RG_BUNDLE_UNREADABLE_OR_INVALID`
- `RG_RULE_NOT_FOUND_OR_NOT_APPLICABLE`
- `RG_REQUIRED_METADATA_FIELDS_MISSING`
- `RN_PLAN_DIGEST_MISMATCH`
- `RN_COLLISION_BLOCKING`
- `RN_DESTRUCTIVE_GUARD_MISSING`

## 4) Documentary non-regression gate before implementation

Any future UI implementation must preserve:
1. Diagnostic IDs and severity semantics from `S3.2-DIAGNOSTICS-REFERENCE.md`.
2. Placement/visibility/CTA intent from `S3.2-DIAGNOSTICS-UI-MATRIX.md`.
3. Operational decision model (`Go`, `Review required`, `No-Go`) aligned with `S3.1-OPERATING-PROFILES.md`.
4. Deterministic priority rule `blocking > warning > info`.
5. Explicit apply blocking whenever blocking diagnostics exist.

If one item above is violated, implementation is considered non-compliant with S3.2 framing.

---

## 5) Minimal implementation readiness

This contract is intentionally short and sufficient to start a small UI evolution batch with no ambiguity on:
- what to show,
- where to show it,
- severity level,
- and operator action behavior.
