# S4.1 Ops Run Rhythm

Date: 2026-04-18  
Perimetre: Orchiviste (routine operateur)

## But du rythme operatoire
Fournir une routine ultra-courte pour executer la chaine Analyse -> Regles -> Renommage
de facon repetitive, lisible et sure, sans ajouter de nouvelle logique.

## Alignement documentaire
- [S3.1 Runbook Rename Chain](S3.1-RUNBOOK-RENAME-CHAIN.md)
- [S3.1 Incident Playbook](S3.1-INCIDENT-PLAYBOOK.md)
- [S3.2 Diagnostics Reference](S3.2-DIAGNOSTICS-REFERENCE.md)
- [S3.5 Apply Readiness Checklist](S3.5-APPLY-READINESS-CHECKLIST.md)

## Pre-run
- Verifier les entrees: dossier source, bundle regles, preset et metadata attendues.
- Verifier les diagnostics deja connus (blocking/warning) dans Pilotage/Historique.
- Verifier les preconditions apply via la checklist S3.5.
- Definir la decision initiale: objectif `preview` d'abord, `apply` seulement si Go.

## Run
- Executer la sequence standard: Analyse -> Regles -> Renommage (preview puis apply controle).
- Surveiller pendant execution:
  - diagnostics bloquants
  - coherence `plan_digest` / `expected_plan_digest`
  - collisions, destination existante, fallback reasons.
- Arret immediat si `No-Go` operateur ou si un diagnostic blocking apparait.

## Post-run
- Verifier les artefacts produits (resultats, metadata, trace regles) et l'historique.
- Verifier que les sorties disque correspondent au resultat attendu.
- Si incident: consigner le symptome et appliquer le playbook incident S3.1.
- Fermer le run en classant le statut: OK, OK avec revue, ou escalation.

## Cas d'arret / escalation
- `plan_digest` mismatch.
- Champs metadata requis manquants.
- Regle introuvable/non applicable, bundle invalide/illisible.
- Collision bloquante ou destination existante non resolue.
- Tout doute operateur sur l'integrite du lot.

## Usage recommande
Utiliser ce rythme pour chaque lot courant.  
Si un point sort du cadre, passer en mode `No-Go` et revenir aux documents S3.1/S3.2/S3.5 avant toute tentative `apply`.
