# S7.6 - Cadrage activation modules Muni

## Objectif

Cadrer strictement l'activation et la desactivation reelles des modules Muni
avant toute implementation. Le but est de permettre une mutation locale simple
du catalogue, sans installer de module, sans changer les moteurs Muni et sans
modifier le contrat canonique `run --request --result`.

## Plus petit perimetre utile

- rendre mutable uniquement l'etat visible d'un module deja connu du registre
  Muni local ;
- permettre `Activer` et `Desactiver` depuis l'App Store Muni pour un module
  deja declare ;
- afficher immediatement le nouvel etat apres mutation ;
- garder l'ouverture de l'outil et la fiche technique separees de la mutation
  d'etat ;
- conserver `Pilotage > Lancer` comme interface expert.

## Preconditions minimales

- le module existe deja dans le registre Muni local ;
- l'identifiant du module est stable ;
- l'etat courant peut etre lu depuis une source locale unique ;
- la mutation peut etre tracee de facon simple ;
- l'UI presente clairement l'effet attendu avant l'action ;
- une action impossible doit rester desactivee et expliquer pourquoi.

## Ce qui peut etre modifie reellement

La seule mutation visee est l'etat local d'activation du module connu :

- `active` : le module reste visible et ouvrable selon ses capacites ;
- `desactive` : le module reste connu, mais n'est plus propose comme action
  courante.

La mutation ne doit pas supprimer le module, modifier ses fichiers, changer son
executable, modifier ses parametres metier ou executer une conversion.

## Hors perimetre

- installation ou desinstallation de modules ;
- telechargement distant ou marketplace ;
- gestion de versions, signatures, licences ou dependances ;
- modification des moteurs Muni ;
- changement du contrat canonique ;
- activation automatique selon disponibilite systeme ;
- activation/desactivation globale multi-modules ;
- refonte du registre ou du cockpit ;
- extension a des droits complexes.

## Risques a eviter

- confondre `desactive` avec `non disponible` ;
- masquer un module au point de perdre sa fiche technique ;
- permettre une mutation sans garde-fou ni confirmation minimale ;
- creer une logique metier parallele a l'execution canonique ;
- rendre l'activation equivalente a une installation ;
- casser les facades employe deja stabilisees ;
- rendre `--quick` ou le parcours local plus lent sans raison.

## Criteres de non-regression

- `/ui/muni/store` reste accessible en lecture simple ;
- `MuniRenommage` et `MuniConversion` conservent leurs liens de facade employe ;
- `Voir la fiche` reste disponible meme pour un module desactive ;
- le badge `Pret employe` reste un statut d'usage, pas un declencheur de
  mutation ;
- les moteurs Muni ne changent pas ;
- le contrat `run --request --result` reste inchange ;
- un module sans facade employe ne devient pas faussement `Pret employe`.

## Decision proposee

Limiter S7.7 a une mutation locale explicite `Activer` / `Desactiver` sur les
modules deja connus du registre Muni, avec affichage clair de l'etat resultant
et sans installation, suppression, moteur modifie ou nouveau workflow.

## Pret a ouvrir S7.7

Le plus petit lot `S7.7` propose est :

`S7.7 - Activation/desactivation locale minimale des modules Muni`

Objectif : rendre les actions `Activer` et `Desactiver` effectivement mutables
dans l'App Store Muni pour les modules connus, en restant strictement borne au
registre local et aux criteres de non-regression ci-dessus.
