# S3.4 Bootstrap (cadrage minimal)

Date: 2026-04-17
Perimetre initial: Orchiviste uniquement (cadrage, pas d'implementation)

## Objectif de S3.4
Passer d'un rendu diagnostics "minimal mais fonctionnel" a un pilotage operateur plus guide, en reutilisant strictement les donnees deja presentes dans Orchiviste.

## Plus petit perimetre utile
- Ameliorer la conduite operateur autour de `preview` / `apply` dans Pilotage.
- Rendre plus explicite le chemin de decision Go/No-Go Apply, sans changer la logique backend.
- Renforcer la lisibilite des actions recommandees avec le cadre documentaire S3.1/S3.2 deja valide.

## Hors perimetre explicite
- Aucun changement de logique metier des outils Muni.
- Aucun changement de generation des diagnostics cote backend.
- Aucun nouveau contrat, aucun refactor transversal UI.
- Aucun nouveau smoke, workflow CI ou configuration.
- Le stash UI reste hors perimetre et inchange:
  - `stash@{0}: wip(ui): cockpit.leaf en attente validation visuelle`

## Dependances sur S3.1 / S3.2 / S3.3
- `S3.1`: base operatoire (runbook, profils, playbook incident).
- `S3.2`: referentiel diagnostics + matrice de rendu + mini-contrat UI.
- `S3.3`: premier patch UI minimal deja livre et stabilise.

## Risques immediats
- Derive de scope vers une refonte UI au lieu d'un micro-lot.
- Incoherence entre libelles UI et recommandations documentaires S3.1/S3.2.
- Surcharge visuelle qui degrade la lisibilite operateur.
- Ajout de comportements implicites non testes (hors perimetre S3.4).

## Ordre d'execution minimal recommande
1. Ouvrir `S3.4-T1` comme micro-lot Orchiviste UI-only.
2. Ajouter un bloc operateur court en Pilotage (rappel Go/No-Go + lien runbook/playbook), sans changer backend.
3. Valider strictement: `swift build`, `swift test`, smokes existants, verification visuelle locale ciblee.
4. Clore `S3.4-T1` avant toute extension.

## Decision proposee
Ouvrir S3.4 avec un seul micro-lot UI operatoire et reversible, limite a Orchiviste.
