# S3.1 Runbook - Rename Chain

Date: 2026-04-16  
Scope: Orchiviste operational guidance only (no code change)

## 1) But du runbook
Fournir une procedure unique, reproductible et non destructive par defaut pour executer la chaine:
- MuniAnalyse
- MuniRegles
- MuniRenommage

Cette procedure definit quand un `preview` est suffisant, quand un `apply` est autorise, et quand il faut s'arreter.

## 2) Prerequis
- Orchiviste operationnel (Pilotage Muni accessible).
- Outils disponibles dans le catalogue:
  - `MuniAnalyse`
  - `MuniRegles`
  - `MuniRenommage`
- Source documentaire preparee sur une copie de travail (jamais les originaux).
- Preset de renommage valide.
- Regle cible `MuniRegles` identifiee (`regles_naming_rule_id`).

## 3) Entrees obligatoires

### 3.1 Etape analyse
- `source_paths` (documents a analyser)
- sortie metadata: `document_metadata_output_path`

### 3.2 Etape regles (bundle)
- `classification_path`
- `rules_path`
- `guide_path`
- sortie bundle: `bundle_path`

### 3.3 Etape renommage (preview/apply)
- `directory_path`
- `preset_path`
- `regles_bundle_path`
- `regles_naming_rule_id`
- `regles_apply_rule=true` (si application de regle MuniRegles voulue)
- `document_metadata_path`
- `dry_run=true` pour preview
- `dry_run=false` + `confirm_apply=true` + `allow_destructive=true` pour apply controle
- `expected_plan_digest` obligatoire en apply (issu du preview)

## 4) Sequence standard

### 4.1 Analyse
1. Lancer `MuniAnalyse` en extraction metadata.
2. Verifier que `document_metadata.json` est genere.
3. Verifier provenance et warnings structures:
   - `extraction_provenance` (`pdf_text`, `filename_fallback`, etc.)
   - warnings exploitables (payload structure, pas seulement texte libre)

### 4.2 Bundle regles
1. Lancer `MuniRegles` pour produire le bundle.
2. Verifier presence de `naming_rule_contracts`.
3. Pour la regle cible, verifier:
   - `rule_id`
   - `template`
   - `required_metadata_fields`

### 4.3 Preview renommage
1. Lancer `MuniRenommage` en `preview` (`dry_run=true`).
2. Verifier metadonnees de trace:
   - `regles_source`
   - `regles_bundle_version`
   - `regles_module_version`
   - `regles_rule_id`
   - `regles_fallback_reason` (si fallback)
   - `plan_digest` (obligatoire)
3. Verifier diagnostics metier:
   - collisions detectees
   - cas idempotents (deja au bon nom)
   - warnings structures

### 4.4 Apply controle
1. Autoriser seulement si criteres de section 8 remplis.
2. Lancer `MuniRenommage` en apply:
   - `dry_run=false`
   - `confirm_apply=true`
   - `allow_destructive=true`
   - `expected_plan_digest=<digest du preview>`
3. Verifier:
   - digest aligne (`plan_digest` == `expected_plan_digest`)
   - aucun overwrite implicite
   - collisions traitees explicitement
   - idempotence respectee

## 5) Garde-fous obligatoires
- Aucune execution destructive sans:
  - `allow_destructive=true`
  - `confirm_apply=true`
- `apply` interdit sans `expected_plan_digest`.
- Si `required_metadata_fields` non satisfaits:
  - ne pas forcer la regle
  - fallback explicite requis.
- Interdiction d'ecrire sur dossiers originaux de production tant que run de validation non cloture.

## 6) Diagnostics attendus
- Statut canonique explicite (`succeeded`, `needs_review`, `failed`).
- Tracabilite de source regles (`muniregles_bundle` ou `fallback_local`).
- Raison de fallback stable (`regles_fallback_reason`).
- Warnings structures (analyse/renommage) lisibles dans historique.
- Informations collisions/idempotence visibles et exploitables.

## 7) Artefacts attendus
- `document_metadata.json`
- bundle `MuniRegles` (incluant `naming_rule_contracts`)
- `request.json` / `result.json` de chaque run
- historique local Orchiviste (`history.jsonl` runtime)

## 8) Conditions minimales pour autoriser apply
Toutes les conditions suivantes doivent etre vraies:
1. Bundle valide et regle cible resolue.
2. `required_metadata_fields` satisfaits pour les documents concernes.
3. Preview termine avec `plan_digest` present.
4. Aucun conflit bloquant non traite (collisions non resolues).
5. Operateur confirme un run sur copie de travail.
6. Apply lance avec `expected_plan_digest` egal au digest du preview valide.

## 9) Cas d'arret (ne pas appliquer)
Arreter et corriger avant apply si au moins un point est vrai:
- bundle invalide/illisible
- metadata absente/invalide
- regle introuvable ou template non applicable
- `required_metadata_fields` manquants
- `plan_digest` absent ou mismatch
- collisions non resolues
- fallback non compris ou warnings critiques non traites
- tentative d'apply sans garde-fous destructifs

## 10) Definition of done (operatoire)
Le lot est considere correctement execute quand:
- la sequence complete est rejouable de facon deterministe,
- les diagnostics sont lisibles dans Pilotage/Historique,
- l'apply ne passe que sous conditions strictes de securite et de coherence.
